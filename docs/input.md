# Вход, расчёт и интерпретация

Все команды работают с локальными файлами; публикация отчёта является отдельным действием.

Публичный `examples/input.json` содержит вымышленные данные и синтетические ответы, не данные автора.

Рабочие входы и результаты сохраняйте в игнорируемом `runs/` либо вне репозитория.

## Подготовка входа

| Поле | Требование |
|---|---|
| `name` | Непустое имя в одном выбранном алфавите |
| `language` | `ru`, `en` или `he`; правила счёта в [arithmetic.md](arithmetic.md) |
| `birth_date` | Реальная дата `YYYY-MM-DD` |
| `birth_time` | Местное время `HH:MM`, либо `null` при неизвестном времени |
| `birth_place` | Непустое название места рождения |
| `timezone` | Установленная IANA-зона, например `Europe/Moscow`; обязательна при известном времени |
| `latitude` | Конечное число строго между −90 и 90, без `bool`; обязательно при известном времени |
| `longitude` | Конечное число от −180 до 180 включительно, без `bool`; обязательно при известном времени |
| `location_source` | Непустое описание источника зоны и координат; обязательно при известном времени |
| `time_accuracy` | `exact`, `approximate` или `unknown` |
| `time_window_minutes` | Только для `approximate`: целое от 1 до 720, половина окна ± в минутах |
| `fold` | Необязательный `0` или `1` для повторяющегося местного времени при переводе часов |
| `as_of` | Явная дата расчёта `YYYY-MM-DD`, не раньше рождения |
| `answers` | Массив ровно из 36 целых оценок 1–5, без `bool`, либо `null` |
| `original_text` | Непустой дословный исходный текст пользователя; не реконструировать его из полей |
| `confirmed` | Строго `true` после проверки человеком сведений, зоны и координат |
| `backend` | Необязательный `astronomy` по умолчанию; `legacy` только явно, без автоматической подмены |
| `true_node` | Необязательный `bool`, по умолчанию `false` — средний узел |

Неизвестные поля отклоняются, даты и время не достраиваются автоматически.

`unknown` требует `birth_time=null` и оставляет Human Design и астрологию недоступными, без полуденной подстановки; зона, координаты и их источник в этом случае могут отсутствовать или быть `null`.

`answers=null` оставляет модуль архетипов недоступным и не мешает остальным расчётам.

Ошибочный ввод, отсутствующая зависимость или ошибка выбранного backend завершают CLI с кодом 2, без успешного частичного результата, скрывающего ошибку.

Несуществующее местное время отклоняется; для неоднозначного времени нужен явный `fold`.

Для `approximate` рассчитывается центральное время и дискретная выборка местного времени от левого края окна через 15 минут, дополненная центром и правым краем.

Если окно пересекает смену даты, образцы используют соответствующую соседнюю дату; попадание в разрыв местного времени вызывает ошибку, а не молчаливый пропуск образца.

В `time_window` сохраняются число образцов, сами образцы и `varied` — изменившиеся основные показатели HD, долготы и знаки планет, ASC/MC.

Совпадение выбранных образцов не доказывает устойчивость на всём интервале; `interval_reliability_established=false`, факты относятся к центральному отсчёту.

## Команды

После установки зависимостей и создания каталога `runs/`:

```sh
.venv/bin/python personality.py calculate --input examples/input.json --output runs/calculation.json
.venv/bin/python personality.py summary --calculation runs/calculation.json
.venv/bin/python personality.py check --calculation runs/calculation.json
.venv/bin/python personality.py render --calculation runs/calculation.json --output runs/report.html
.venv/bin/python personality.py questionnaire
```

`questionnaire` выводит шкалу и все 36 вопросов без ключа подсчёта.

`summary` выводит компактные факты, статусы модулей, ограничения и provenance, без исходного текста, имени и полного набора активаций.

`render` без интерпретации создаёт честно обозначенный расчётный черновик.

Если подготовлен отдельный JSON интерпретации:

```sh
.venv/bin/python personality.py check --calculation runs/calculation.json --narrative runs/narrative.json
.venv/bin/python personality.py render --calculation runs/calculation.json --narrative runs/narrative.json --output runs/report.html
```

Выходной файл должен отличаться от всех входных, включая символические ссылки и жёсткие ссылки на тот же файл.

Запись выполняется атомарной заменой временного файла в каталоге назначения; каталог должен уже существовать.

JSON с повторяющимися ключами, NaN, Infinity и переполнением чисел отклоняется.

## Контракт расчёта

`calculate(input_dict)` возвращает объект с `schema_version=2`, `calculation_id`, `input`, `as_of`, `modules`, `facts`, `warnings` и `provenance`.

В версии 2 модулей по-прежнему пять: `human_design`, `gematria`, `numerology`, `astrology`, `archetypes` всегда присутствуют со статусом `computed` или `unavailable`; у недоступного модуля есть `reason`, его `data` пуст, фактов от него нет.

Полные промежуточные данные находятся в `modules`, а сводные факты имеют стабильные `id`, `section`, `label`, `value` и необязательный текст `detail`.

Идентификаторы включают `gem.total`, `num.life_path`, `num.matrix.1`…`num.matrix.9`, `arch.1`…`arch.12`, `hd.type`, `hd.profile`, `hd.authority`, `hd.channels`, `hd.centers`, `astro.sun.longitude` и соответствующие долготы остальных девяти планет.

Номер архетипа относится к порядку исходного ключа, а не к рангу текущего профиля; `detail` факта сохраняет его плотный ранг.

Источники `num.cycle.*`, `num.pinnacle.*`, `num.challenge.*`, `num.personal.*` относятся к разделу `life_cycles`, производному от модуля `numerology`; шестой расчётный модуль не создаётся.

Дополнительные источники Human Design: `hd.personality.sun`, `hd.personality.earth`, `hd.design.sun`, `hd.design.earth` содержат `value={"gate": число, "line": число}`.

`hd.design_date` содержит UTC ISO-момент дизайна из `provenance.design_utc_iso`, рассчитанный по солнечной дуге 88°; эти факты отсутствуют при неизвестном времени рождения.

`calculation_id` — SHA-256 UTF-8 канонического JSON всего расчёта без самого `calculation_id`: `ensure_ascii=False`, `sort_keys=True`, `separators=(',', ':')`, `allow_nan=False`.

Перед `check`, `render` и `summary` идентификатор проверяется; изменение любого входного поля, факта или ограничения требует пересчёта и новой привязки интерпретации.

Хеш обеспечивает обнаружение изменений и привязку файлов; он не является подписью автора и не доказывает истинность самостоятельно отредактированных данных.

## Контракт интерпретации

JSON интерпретации содержит `calculation_id` текущего расчёта, `sections` со всеми восемью разделами и непустой `summary` для общего итога в конце отчёта.

Порядок разделов: `human_design`, `gematria`, `numerology`, `astrology`, `life_cycles`, `archetypes`, `purpose`, `finance`.

После восьми разделов располагается заключение — общий итог, представленный `summary` и тематическими блоками `summary_topics`; исходные данные открыто показываются в начале.

Раздел `life_cycles` не объявляется недоступным из-за отсутствия собственного модуля: он использует расчёт нумерологии.

Каждый раздел содержит непустой `intro`, непустой список `interpretation` и список `actions`.

Один элемент списка имеет вид:

```json
{"text": "Объяснение конкретного наблюдения.", "sources": ["num.life_path"]}
```

Все ссылки должны существовать в `facts`; для рассчитанных разделов, синтеза и итоговой сводки каждый элемент требует хотя бы один источник, а списки не могут быть пустыми.

Для недоступного аналитического модуля объяснение отсутствия данных в `interpretation` может иметь `sources=[]`, а `actions` может быть пустым списком.

Если у недоступного модуля всё же указаны действия, они также требуют существующих источников; отсутствие данных не создаёт оснований для синтеза.

Дополнительно в каждом разделе допускается `topics` — непустой список тематических блоков с непустым `title` и непустым списком `paragraphs`.

Каждый абзац темы имеет ту же структуру `{text, sources}`, что и элемент `interpretation`; источники должны существовать, пустые ссылки допускаются только в объяснении недоступного аналитического модуля.

Для `life_cycles`, `purpose` и `finance` пустые ссылки не допускаются.

В заключении используется необязательный `summary_topics` той же структуры, всегда с непустыми источниками у каждого абзаца.

Пример тематического блока:

```json
{
  "title": "Жизненный путь и имя",
  "paragraphs": [
    {"text": "Объяснение связи двух рассчитанных показателей.", "sources": ["num.life_path", "num.destiny"]}
  ]
}
```

`topics` и `summary_topics` дополняют обязательные `intro`, `interpretation`, `actions` и `summary`, а не заменяют их.

Версия 1 отклоняется: после изменения схемы и разделов нужно заново выполнить расчёт, а затем перепривязать интерпретацию к новому `calculation_id`.

`check` проверяет структуру, хеш и существование связей; он не выполняет семантическую вычитку и не доказывает, что процитированный факт обосновывает вывод.

Смысловую обоснованность, понятность и пригодность рекомендаций проверяет отдельный редакторский проход.

## Проверка разработки

```sh
.venv/bin/python -m unittest discover -s tests -v
git diff --check
```

Тесты оркестратора используют явно синтетический backend для проверки передачи данных; точность реального астрономического адаптера проверяется отдельными тестами.

CLI-прогон примера дополнительно проверяется на установленном реальном backend.
